# Organisations

Signaculum organisations group people for SSO apps. Membership roles appear on the OpenID Connect `orgs` claim when the client requests the `qiick.orgs` scope.

Reserved, case-insensitively after normalisation: the first path segment of every route (`admin`, `api`, `oauth`, `well-known`, `login`, `settings`, …), the names in `public/`, system names (`www`, `mail`, `root`, `administrator`, `support`, `help`, `status`, `security`, …) and every slug of 1–2 characters. A slug taken before it was reserved stays valid until it is changed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **name**            | Display name in the UI.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **is_mfa_required** | When true, members must enroll TOTP or a passkey **and** prove a second factor in the current session `amr` (`mfa`, or passkey `hwk`/`swk`) before finishing OAuth authorization. Enrolment alone is not enough; email-code-only or password-only sessions are stepped up (login toast explains the loop). With `prompt=none`, the client gets `interaction_required` and the session stays intact. `amr` / `acr` stay truthful. The requirement holds whatever `config/fortify.php` enables: only an enabled method counts (TOTP off → passkeys only), and with neither TOTP nor passkeys enabled members are refused with an explanation (`access_denied` for `prompt=none`); Settings → Authentication & security then lists the affected organisations. Turning it **on** (false → true only; create never sets MFA) revokes every member's access tokens, refresh tokens and unredeemed authorization codes (logged as `organization_member_tokens_revoked`), then queues back-channel logout for every open OIDC session of those members (logged as `organization_member_backchannel_logout_dispatched`). **Adding** a member (UI, Admin API, or invitation acceptance) to an organisation that already requires MFA revokes that user's grants the same way and queues the same per-user back-channel job; joining an organisation without MFA changes nothing. Clients with a back-channel logout URI are signed out; apps without one keep their own session until it expires because front-channel logout needs the member's browser. The acting owner's Signaculum web session stays intact so the authorize gate can step them up (#163, #174). |

Members may hold one or more of: `owner`, `admin`, `member`, `billing` (Decision 2026-11-13). Every organisation must keep **at least one `owner`**.

## UI

Signed-in users manage organisations they belong to under **Organisations**:

- **Members** — list, add/remove roles, leave (guards prevent removing the last owner).
- **Invitations** — email invite with a hashed token, expiry (default seven days, `OIDC_ORG_INVITATION_TTL_DAYS`), resend and revoke.
- **Settings** — name / slug, optional MFA requirement, branding and other org settings.
- **Delete** (owner, or `can-manage-organizations`) — an offboarding, not a database cascade (#289). Under a lock on the organisation row it revokes every member's access tokens, refresh tokens and unredeemed authorization codes and queues back-channel logout for their open OIDC sessions (as when MFA is turned on), deactivates the organisation's principals as `offboarded`, revokes the API keys they own, removes memberships and pending invitations, sends one `organization.membership_changed` webhook (`removed`) per member, and soft-deletes the organisation. Principals and audit rows stay as evidence, the slug cannot be used again, and there is no restore: a mistaken delete needs a new organisation with a new slug. Adding a member takes the same lock and refuses a deleted organisation.

Instance admins may also create organisations as part of day-to-day ops; invitations are rate-limited.

## `qiick.orgs` claim

Clients that request scope `qiick.orgs` receive on the `id_token` and userinfo:

```json
"orgs": [
  { "id": "…", "slug": "acme", "roles": ["owner", "billing"] }
]
```

- Empty list when the user has no memberships.
- Sorted by `slug`.
- Role strings match the enum above.

[`qiick/laravel-oidc`](https://github.com/qiick-io/laravel-oidc) can map `orgs` into app roles (`oidc.roles.*`, with `organization` set to the id or slug this app belongs to). Add `qiick.orgs` to `oidc.scopes` on the client.

Wire details: [OIDC profile](./oidc-profile.md).
